# JoyWord 重构方案

日期：2026-11-03。目标是在当前目录构建 GPUI 桌面版 JoyWord，最终作为 JoyOffice 的 Word 子应用，替换现有 `apps/joyword` 和相应产品模块。完整拆分见 [112 项任务](TASKS.md)。

## 核心结论

采用“Wordcraft 核心能力迁入＋JoyOffice UI 和桌面能力复用＋分阶段整合”的路线。Wordcraft 已是 Rust 项目，本次主要工作是 UI 框架迁移、两套接口适配、依赖对齐及原有功能回归。现 JoyWord 的桌面代码提供成熟的接入起点，但其模型、命令和保存绑定不能直接替换 Wordcraft 对应类型。

GPUI 用于应用外壳和页面呈现，GPUI Kit 提供组件入口，`joyoffice-ui` 提供公共视觉规范。正文整形、断行和分页仍由文档内核负责。只有一套可编辑文档和撤销历史；旧模型只在必要时用于隔离的只读旧数据转换。

最终功能范围采用两个来源的能力并集：保留 Wordcraft 已有功能，同时保留现 JoyWord 的既有用户流程、保护、安全保存、恢复、可访问性和已提供的 AI 开关/自动化契约。Wordcraft 原来尚未完成的 Word 对齐项继续登记，不因本次迁移承诺全部补齐；迁移新增回退须逐项修复或由用户明确调整范围。

## 技术路线和关键约束

1. **先可运行，再扩大功能覆盖。** R1 启动真实 GPUI 窗口；R2 打开真实文档；R3 编辑并安全保存。每个后续阶段保留这些能力。
2. **复用经过接口检查的代码。** 公共 UI 可以原样复用；现 JoyWord 的 Ribbon、IME、页面调度、保存等通过新内核适配；旧模型、旧 engine 和旧布局不成为第二套长期内核。
3. **依赖先试验再大规模导入。** Wordcraft 与宿主的字体/PDF/容器依赖存在冲突，engine 还依赖格式和 PDF。必须迁入完整编译闭包；不能先只复制 engine，再遇到无法解析的依赖。
4. **屏幕和 PDF 共享场景。** R2 以 CPU 光栅页面接入 GPUI，形成可靠显示基线；R6 验证 GPUI 原生字形、路径和纹理优化。光标与选区独立叠加。
5. **以真实呈现衡量性能。** 原 egui 版也有 GPU 窗口，正文主要经过 CPU 光栅。换 UI 框架不会自动解决排版、光栅和上传瓶颈；性能结果按相同设备和字体实测。
6. **从早期持续演练宿主整合。** R2、R3、R4 即演练宿主依赖和构建；R8 执行最终替换。当前目录不写死外部绝对路径依赖。
7. **质量契约同时保留。** 延续 Wordcraft 的无生产 panic、恶意输入和 typing 回归，保留 JoyWord 的未知内容保留、安全保存、任务代次和 AI 默认关闭约定。
8. **生产桌面依赖不含 egui。** 旧 egui 界面可作为只读参考和外部对照程序，不能成为新 UI 的运行时嵌入层。原网页/BSD 入口不自动成为 GPUI 桌面的支持承诺；核心 WASM 能力可保留独立检查。

R0 是工程基线阶段；R1 起每阶段交付新 JoyWord 桌面包。R6 在 R2 后开始，R7 在 R1 后开始，持续伴随功能迁移；不必等 R5 全部完成才处理性能和平台问题。允许较早对某个 R6/R7 切片出包，但必须注明其依赖的功能阶段。

实施顺序为 R0 → R1 → R2 → R3 → R4 → R5，再汇合 R6/R7 的最终验收进入 R8。完整依赖以 [tasks.json](tasks.json) 为准。

## 构建和演示节奏

每个切片保持可构建；不将大批未编译改动推到阶段末尾。每阶段提供如下证据：

- 带源码指纹的桌面开发包、运行命令和变更范围。
- 从包启动的截图或操作记录，以及可重开的示例文档。
- 相应 core/CLI/UI 自动检查结果，保存/恢复等场景的故障回归。
- 与上个阶段相比的新能力、仍未迁入的功能和各平台验证状态。
- 从 R2 开始的短性能冒烟；阶段验收执行较完整语料和性能检查。

包放在 `dist/joyword/Rn/`，应用身份始终为 JoyWord。阶段号进入归档名称和 About 构建信息，不进入 Cargo 包名或正常模块名。未发布候选使用隔离的试用配置目录，避免覆盖现 JoyWord 的偏好和恢复数据。

## 复用优先级

优先顺序是公共组件 → 现 JoyWord 的纯视图和平台接线 → shell 中可抽离的通用行为 → 两来源测试和语料。细项、限制和任务链接见 [REUSE.md](REUSE.md)。

不会为“复用率”引入依赖旧文档模型的整块实现。对于旧 shell 的 InputBackend、DocxSession、PageScene 和 ExportPlan，先定义新内核边界，再抽取可复用逻辑；不在每次按键时进行两套文档模型互转。

## 集成方式

独立开发期间采用与宿主相同的 `apps/`、`crates/`、`docs/joyword/` 布局。公共库可按宿主固定提交复制到相同路径作为迁移期快照，并登记来源/散列；最终合入使用宿主现有库，删除重复副本。不得用 `D:\Coding\...\joyoffice` 绝对路径形成只能在本机编译的产品。

R8 在最新宿主的独立集成分支或工作区准备替换，保留旧 Word 的源码及可运行包作为回退基线。解决现有 `joyword-model`、`joyword-engine` 等同名包冲突后，更新根锁、产品工程工具和文档；修改公共内容时回归 Word、Deck、Sheet 及联合 feature 组合。整合后开发入口转移至 JoyOffice，当前独立目录归档，不保留第二条持续开发线。

## 排期和估算办法

优先以 R3 为第一项可实际写作的里程碑，R4 为常用功能预览，R8 为宿主替换里程碑。R0/R1 完成后，用实测的依赖适配和单个 UI 切片成本估算 R2/R3；R3 后再估算剩余复杂 UI。R5 的大量功能入口及 R6 的原生字形身份验证是主要不确定项。

本次不直接使用 Wordcraft 上游 roadmap 的小时数：它估算的是原 egui 产品的后续完善，不能代表本次框架迁移和旧 JoyWord 兼容成本。任务可按接口边界交错实施；是否安排多人并行由实际执行安排决定。
